# Сценарный анализ смены

Дополнительное задание кейса: ответить на вопросы

- «что будет, если на смену выйдет на 3 сотрудника меньше»;
- «какой запас АО нужен в рюкзаке, чтобы не заезжать в СЦ».

Сценарий считается по тем же данным и тем же солвером, что и рабочий план, но
**не изменяет** план дня, события, версию плана и состояние хранилища.

## REST API

```
POST /api/v1/days/{date}/scenarios
Content-Type: application/json
```

Дополнительный эндпоинт вне контракта организаторов; основные методы
(`/reference`, `/days`, `/days/{date}/plan`, `/days/{date}/events`) не меняются.

### Тело запроса

Все поля необязательны.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `staff_delta` | integer ≤ 0 | Сколько сотрудников не выйдет на смену. `-3` — убрать трёх наименее загруженных. |
| `excluded_staff_ids` | string[] | Явный список выбывающих сотрудников. Имеет приоритет над `staff_delta`. |
| `equipment_start` | `{ONT, ROUTER, STB}` | Задать одинаковый стартовый запас АО всем сотрудникам. |
| `equipment_capacity` | `{ONT, ROUTER, STB}` | Задать одинаковую вместимость рюкзака всем сотрудникам. |
| `use_recommended_equipment` | boolean | Подставить рекомендованный запас АО из базового плана. Нельзя совмещать с `equipment_start`. |
| `time_limit_sec` | integer | Лимит решения одного плана, по умолчанию 5 с (максимум 60 с). |

Если не передан ни `excluded_staff_ids`, ни `staff_delta`, состав смены не
меняется: сервис сравнивает базовый план с ним же и возвращает рекомендацию по
запасу АО.

### Ответ

| Поле | Назначение |
| --- | --- |
| `baseline` | Метрики базового плана. |
| `scenario` | Метрики сценарного плана. |
| `delta` | Разница `scenario − baseline` по назначениям, нераспределённым нарядам, попаданиям в слот и срок, пробегу, времени в пути, CV загрузки и заездам в СЦ. |
| `excluded_staff_ids` | Кто не вышел на смену в сценарии. |
| `newly_unassigned` | Наряды, которые были назначены в базе, а в сценарии остались без исполнителя, с причиной. |
| `equipment_recommendation` | Рекомендация по запасу АО по каждому сотруднику и суммарный дефицит. |
| `scenario_plan` | Полный план сценария (маршруты, остановки, сводка). Это гипотетический план, он не сохраняется. |

Метрики одного плана:

- `staff_count`, `orders_total`, `visits_planned`, `unassigned`, `pgp_orders`;
- `slot_hits` / `slot_hit_rate` — визиты, начатые внутри слота;
- `deadline_hits` / `deadline_hit_rate` — визиты, завершённые в контрольный срок;
- `travel_sec_total`, `distance_m_total`;
- `utilization_cv` — коэффициент вариации загрузки сотрудников;
- `restock_stops`, `restock_min` — заезды в СЦ за АО и время на них.

### Пример

```bash
curl -s -X POST http://localhost:8080/api/v1/days/2026-10-26/scenarios \
  -H 'Content-Type: application/json' \
  -d '{"staff_delta": -3, "time_limit_sec": 5}'
```

Подобрать запас АО и проверить, что заезды в СЦ исчезнут:

```bash
curl -s -X POST http://localhost:8080/api/v1/days/2026-10-26/scenarios \
  -H 'Content-Type: application/json' \
  -d '{"staff_delta": -3, "use_recommended_equipment": true}'
```

## Как выбираются выбывшие сотрудники

Без явного списка сервис убирает **наименее загруженных** сотрудников базового
плана: сначала по числу визитов, затем по коэффициенту загрузки, затем по
`staff_id`. Это делает сценарий детерминированным и воспроизводимым.

## Как считается рекомендация по АО

Для каждого маршрута базового плана суммируется потребность в АО по всем
визитам:

```
required_start = Σ required_equipment(visits)
```

Если стартовый запас (`equipment_start`) меньше этой суммы, рюкзак закончится и
понадобится заезд в СЦ. Поэтому:

```
additional_start    = max(0, required_start − current_start)
required_capacity   = max(current_capacity, required_start)
additional_capacity = max(0, required_capacity − current_capacity)
```

Рекомендация считается по базовому плану. После изменения состава смены маршруты
могут перераспределиться, поэтому фактический дефицит в сценарии может
отличаться — для проверки используйте `use_recommended_equipment: true`: сервис
подставит рекомендацию и пересчитает план.

## Интерфейс диспетчера

Раздел **«Сценарии»** (`/scenarios`):

- ползунок «на сколько меньше сотрудников»;
- выбор запаса АО: текущий, рекомендованный или свой;
- сравнение метрик «база → сценарий» с подсветкой ухудшений;
- список новых нераспределённых нарядов с причинами;
- таблица рекомендаций по рюкзакам с дефицитом по каждому сотруднику;
- загрузка маршрутов сценария.

## Конфигурация

```yaml
dispatch:
  scenario:
    time-limit-sec: 5
    max-time-limit-sec: 60
```

## Ограничения

- Базовый и сценарный планы решаются заново, поэтому запрос занимает примерно
  два лимита решения (по умолчанию около 10 с).
- Одновременно выполняется только один сценарный расчёт; параллельный запрос
  получает `409 Conflict`.
- Сценарий не учитывает уже начатые визиты как отдельный префикс: это
  гипотетический план на день. Рабочий план с префиксом выполненной части
  по-прежнему доступен через `POST /events`.
- Рекомендация по АО — оценка по базовому плану, а не гарантия для любого
  перераспределения нарядов.

## Проверки

```bash
cd backend && ./gradlew test --tests '*ScenarioApiTest'
```

Тест проверяет:

- сценарий с `staff_delta = -1` убирает единственного сотрудника и показывает
  новые нераспределённые наряды;
- рекомендация по АО возвращается по базовому плану;
- рабочий план и его версия после сценария не меняются;
- некорректные параметры дают `400`/`422`.
