# Архитектура сервиса «Умная диспетчеризация»

Документ описывает, как устроен backend: слои, поток данных, точки расширения и принятые
технические решения. Все имена классов и пакетов — реальные, из `backend/src/main/java`.

## 1. Общая схема

```
Angular (диспетчер)                Оркестратор организаторов
        │                                   │
        └────────── HTTP/JSON ──────────────┘
                        │
              ┌─────────▼──────────┐
              │  web/  (Spring MVC)│   контроллеры, обработка ошибок, CORS
              └─────────┬──────────┘
                        │
        ┌───────────────┼────────────────┐
        │               │                │
   web/plan/       web/events/      web/pgp/
 PlanningService  EventProcessor   PgpDetector
 PlanAssembler                    (группировка по узлу доступа)
 PlanMerger
        │               │
        └───────┬───────┘
                │
      web/storage/InMemoryDataStore   ← состояние прогона
                │
      service/DaySolutionFactory      ← единственная сборка домена из DTO
                │
   domain/model  +  domain/constraint  ← модель и ограничения Timefold
```

Внешних зависимостей у сервиса две: HTTP-клиент (фронт или оркестратор) и матрица времени
в пути, которую присылают организаторы. БД нет — см. п. 5.

## 2. Слои и их ответственность

| Пакет | Ответственность | Чего там быть не должно |
|---|---|---|
| `dto/` | Точное отражение `api_spec.yaml`: имена полей, типы, `OffsetDateTime` | логика, расчёты |
| `domain/model/` | Модель задачи для солвера: `DaySolution`, `Staff`, `Visit`, `Order`, `WorkType`, `Shift`, `TravelMatrix` | HTTP, JSON |
| `domain/constraint/` | `DispatchConstraintProvider` — ограничения и целевая функция | работа с временем/маршрутом «вручную» |
| `service/` | `DaySolutionFactory` — DTO → домен, валидация входных данных | знание про HTTP-статусы |
| `web/plan/` | Оркестрация расчёта: сборка задачи, запуск солвера, сборка ответа, склейка с выполненной частью | JSON-маппинг |
| `web/events/` | Валидация и применение событий, вычисление выполненного префикса | сам расчёт плана |
| `web/storage/` | Состояние прогона: справочники, день, план, события, отмены, версии | бизнес-логика |
| `web/` | Контроллеры, `ApiExceptionHandler`, `WebConfig` (CORS) | расчёты |

Правило, которое держим: **время и маршрут считаются только в домене** (`Visit.timingsSupplier`),
а `web/*` занимается оркестрацией. Исключение — `PlanMerger`/`PlanAssembler`, которые
пересобирают остановки после склейки префикса (иначе суммы и последовательность разъедутся).

## 3. Поток одного запроса

### `POST /api/v1/days/{date}/plan`

1. `PlanningService.plan(date)` — проверка, что день загружен и событий ещё не было (иначе `409`).
2. `effectiveDay(...)` — базовые наряды дня минус отменённые плюс пришедшие `NEW_ORDER`,
   плюс сотрудники, выбывшие по `STAFF_UNAVAILABLE`.
3. `PgpDetector.detect(...)` — наряды, похожие на групповую проблему, вынимаются из пула
   планирования и уходят в `pgp_groups`.
4. `DaySolutionFactory.build(...)` — DTO → `DaySolution` (сотрудники, визиты, матрица, `now`).
5. `solverFactory.buildSolver().solve(problem)` — Timefold, лимит из `application.yml`.
6. `PlanAssembler.assemble(...)` — маршруты, остановки, `unassigned` с причинами, сводка.
7. `PlanMerger.merge(...)` — если это перепланирование, в начало маршрута вклеивается
   выполненный префикс; затем `withDayState` (отмены) и `withAlerts` (`LATE_RISK`).
8. `resummarize(...)` — сводка пересчитывается уже по полным маршрутам.
9. `store.savePlan(...)`, ответ 200.

### `POST /api/v1/days/{date}/events`

1. Валидация: тип события, известность наряда/сотрудника, порядок `timestamp`, для
   `VISIT_DELAYED`/`ORDER_TRANSFERRED` — что визит уже начат и что `end` корректный.
2. Идемпотентность: `addEventIfAbsent` — повтор `event_id` возвращает `200 duplicate=true`
   без изменения состояния.
3. `apply(...)` — событие меняет состояние хранилища (отмена, новый наряд, конец визита,
   недоступность сотрудника).
4. `completedPrefix(...)` — из предыдущего плана собирается всё, что уже началось:
   `DEPOT_START`, визиты со `start < timestamp`, завершённые перерывы. Это и есть
   «сохранение уже выполненной части плана».
5. `planning.replan(...)` — тот же путь, что и построение плана, но с префиксом и
   уменьшенным лимитом солвера (5 с), чтобы уложиться в 10 с на событие.
6. `plan_version` увеличивается на 1, ответ `EventResult`.

## 4. Конкуренция и согласованность

- Состояние — `ConcurrentHashMap`/`AtomicReference` в `InMemoryDataStore`; одна загрузка дня
  не мешает другой дате.
- Расчёт защищён `ReentrantLock` в `PlanningService`: параллельный запрос получает `409`
  «Планирование уже выполняется», а не портит план.
- `POST /plan` после первого события запрещён (`409`) — по спеке план дальше меняется
  только событиями.
- Порядок событий проверяется по максимальному `timestamp`; событие «из прошлого» отклоняется.

## 5. Где хранится состояние

По умолчанию состояние лежит в PostgreSQL: справочники, матрица времени в пути, наряды дня,
планы, события, отмены, предупреждения и версии — по одной строке JSONB на сущность
(`web/storage/PostgresDataStore`). Схема создаётся при старте из `schema.sql`, а пустая база
заполняется файлами из `data/` (`config/DataSeeder`).

Несколько дней живут одновременно: состояние разложено по дате, и загрузка нового дня сбрасывает
план, события и версии только этой даты. Требования держать несколько дней активными нет
(«сервис обязан держать как минимум один активный день»), поэтому такого разрешения достаточно.

Для тестов и отладки есть `InMemoryDataStore` (`vrptw.storage.mode=memory`) — он же служит
аварийным режимом, если PostgreSQL недоступен: контракт API при этом не меняется.

Отдельно стоит помнить про размер: матрица организаторов — около 20 МБ, и её разбор самая
дорогая операция в обработке события, потому что лимит на событие — 10 секунд.

## 6. Конфигурация

`backend/src/main/resources/application.yml`:

```yaml
server.port: 8080
timefold.solver.termination.spent-limit: 30s   # лимит основного расчёта
dispatch.team: "С-42"
dispatch.version: "0.1.0"
dispatch.pgp.min-orders: 3        # сколько нарядов с узла считаем группой
dispatch.pgp.window-minutes: 120  # окно регистрации нарядов группы
```

Второй, «короткий» солвер создаётся в `PlanningService` кодом: 5 с на перепланирование,
чтобы ответ на событие укладывался в лимит 10 с.

## 7. CORS и фронт

`web/config/WebConfig` разрешает любые источники `http://localhost:*` и `http://127.0.0.1:*`:
браузер присылает `Origin` даже на same-origin POST, а dev-сервер Angular может занять
произвольный порт — при жёстком списке портов `POST /plan` из браузера получал `403`.
Авторизации в ТЗ нет — `security: []` в спеке.

## 8. Точки расширения

| Что нужно | Куда добавлять |
|---|---|
| Новое ограничение | `DispatchConstraintProvider`, отдельный метод + `asConstraint("...")` |
| Новый тип события | `EventProcessor.TYPES`, ветка в `apply`, при необходимости поле в `InMemoryDataStore` |
| Новый код причины `unassigned` | `PlanAssembler.classify` (порядок проверок = приоритет причины) |
| Другая эвристика ПГП | `PgpDetector` (сейчас — кластеризация по узлу и окну регистрации) |
| Постоянное хранение | заменить `InMemoryDataStore` на репозиторий, интерфейс вызовов уже изолирован |

## 9. Известные ограничения

- **`RESTOCK` не реализован**: заезд в СЦ за АО не планируется, ограничение H7 проверяется
  как «сумма потребностей ≤ стартовый запас» (`equipmentOverflow`). На больших днях это
  может стоить нарядов и штрафов.
- **`STAFF_UNAVAILABLE.until` не учитывается**: сотрудник выбывает до конца дня.
- **H2 проверяется по возврату в СЦ последнего визита**, а не по каждой остановке.
- **Нет отдельного ограничения H9/H10**: H9 выполняется конструкцией (наряд либо в маршруте,
  либо `unassigned`, либо в ПГП, либо `cancelled`), H10 — склейкой префикса.
- **Масштаб скрытого набора (350–450 нарядов/день) не прогонялся**; проверялись дни по 5 нарядов
  и мок-данные.
