# Нагрузочный прогон на реальном масштабе

**Дата:** 2026-11-15
**Цель:** проверить, укладываются ли `POST /plan`, `POST /events` и `GET /plan`
в лимиты жёсткого контракта на масштабе скрытого набора — 3 рабочих дня по
350–450 нарядов и матрица перемещений на 1265 точек.

## Итог

Все лимиты выполнены:

| День | нарядов | POST /plan, с | событий | события: min / медиана / max, с | GET /plan, с | все коды 200? |
| --- | ---: | ---: | ---: | ---: | ---: | :---: |
| 2026-10-27 | 400 | 30,62 | 9 | 6,02 / 6,11 / 8,15 | 0,024 | да |
| 2026-10-28 | 400 | 30,60 | 9 | 6,06 / 6,11 / 6,27 | 0,017 | да |
| 2026-10-29 | 400 | 30,60 | 9 | 6,00 / 6,07 / 6,12 | 0,021 | да |

- **`POST /plan` ≤ 300 с** — фактически ≈ 30,6 с (лимит солвера 30 с + ~0,6 с
  на чтение и разбор данных). Запас ~10×.
- **`POST /events` ≤ 10 с** — худшее событие 8,15 с, типичное ≈ 6,1 с.
  Ни одно событие не вышло за 10 с. Запас у худшего замера — 1,85 с.
- **`GET /plan` ≤ 30 с** — максимум 0,024 с. Запас более чем 1000×.

Худший замер — `VISIT_DELAYED` 2026-10-27 в 10:01: 8,15 с по HTTP
(`processing_ms = 8140`). Остальные события этого дня и все события двух других
дней — 6,0–6,3 с. Похоже на разовый эффект JIT/GC на первом событии с уже
начатым визитом; повторный прогон такого выброса не дал.

Память и CPU процесса JVM (замер после каждого дня):

| День | RSS JVM, МБ | CPU, % (среднее за жизнь процесса) |
| --- | ---: | ---: |
| 2026-10-27 | 190,3 | 96,1 |
| 2026-10-28 | 199,1 | 112,8 |
| 2026-10-29 | 195,6 | 95,2 |

JVM занимает ~200 МБ RSS и утилизирует примерно одно ядро — солвер работает в
одном потоке, разбор JSON идёт последовательно с решением.

## Что именно измерялось

На каждый день, последовательно:

1. `PUT /api/v1/reference` — 0,03–0,08 с;
2. `PUT /api/v1/reference/travel-matrix` — 1,30–1,35 с (15,4 МБ JSON);
3. `PUT /api/v1/days/{date}` — 0,03–0,04 с (400 нарядов);
4. `POST /api/v1/days/{date}/plan` — главный замер дня;
5. 9 событий по возрастанию `timestamp`:
   `TIME_TICK`, `NEW_ORDER`, `VISIT_DELAYED`, `ORDER_TRANSFERRED`,
   `STAFF_UNAVAILABLE`, `TIME_TICK`, `NEW_ORDER`, `VISIT_DELAYED`, `TIME_TICK`;
6. после каждого события — `GET /api/v1/days/{date}/plan`;
7. в конце — ещё один `GET /api/v1/days/{date}/plan`.

Время HTTP — полное время запроса вместе с передачей тела ответа (аналог
`curl -w '%{time_total}'`). Дополнительно сохранён серверный
`processing_ms`, он совпадает с HTTP-временем в пределах 20–30 мс.

## Набор данных

Сгенерирован скриптом `loadtest/generate_loadtest.py` (в git не коммитится):

- **3 дня** — `2026-10-27`, `2026-10-28`, `2026-10-29`, по **400 нарядов**,
  `now = 08:30+05:00`, слоты внутри дня, уникальные `order_id`;
- **справочник** — 5 СЦ, 40 сотрудников, 8 типов работ, **1260 домов**
  (расширен с 100, чтобы соответствовать размеру матрицы);
- **матрица** — **1265 × 1265** точек (5 СЦ + 1260 домов), 0 по диагонали,
  10–40 минут между точками (600–2400 с), расстояния при средней скорости
  ~20 км/ч. Размер JSON — **15,4 МБ**, в PostgreSQL JSONB — 7,9 МБ.

Данные лежат в `loadtest/` и не попадают в демо-интерфейс. В БД загружаются
через PUT-запросы (`VRPTW_SEED_ENABLED=false`), а не сидером.

### Оговорка про состав дня

400 нарядов дня включают дубликаты шаблонных нарядов, поэтому детектор ПГП
объединил 144 наряда в 38 групп. Солвер фактически оптимизировал 258 визитов,
142 попали в маршруты, 116 остались нераспределёнными. На замеры это влияет
слабо: лимит решения фиксирован (30 с / 5 с), а разбор матрицы и справочника
не зависит от числа нарядов. Но активный набор визитов был меньше 400 —
это стоит учитывать при интерпретации качества плана (время, а не качество,
здесь главная метрика).

## Окружение

- macOS (arm64), Docker Desktop;
- PostgreSQL 16.16 в контейнере `rostelecom-postgres` (`docker compose up -d postgres`),
  отдельная БД `vrptw_loadtest`, чтобы не затронуть общую демо-БД;
- backend — `./gradlew bootRun`, Java 21 (Temurin/Homebrew), порт **8086**,
  `VRPTW_STORAGE_MODE=postgres`, `VRPTW_SEED_ENABLED=false`;
- конфигурация солвера без изменений: `POST /plan` — 30 с, replan по событию — 5 с;
- общий том `pgdata` не удалялся.

## Как воспроизвести

```bash
# 1. Данные (в git не коммитятся)
python3 loadtest/generate_loadtest.py

# 2. PostgreSQL (общий том не трогаем)
docker compose up -d postgres
docker compose exec -T postgres psql -U vrptw -d vrptw \
  -c "CREATE DATABASE vrptw_loadtest"   # один раз

# 3. Backend на свободном порту
cd backend
JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home \
VRPTW_STORAGE_MODE=postgres \
SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/vrptw_loadtest \
SPRING_DATASOURCE_USERNAME=vrptw SPRING_DATASOURCE_PASSWORD=vrptw \
VRPTW_SEED_ENABLED=false \
VRPTW_DATA_DIR="$(pwd)/../loadtest" \
SERVER_PORT=8086 \
./gradlew bootRun

# 4. Прогон (в другом терминале)
python3 loadtest/run_loadtest.py
```

Результаты прогона сохраняются в `loadtest/results.json`; скрипты и данные
исключены из git через `.gitignore`.

## Бонус: `JAVA_OPTS` в контейнере

В `docker-compose.yml` был задан `JAVA_OPTS=-Xmx2g -Xms512m`, но
`backend/Dockerfile` запускает приложение в exec-форме:

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
```

В такой форме переменная `JAVA_OPTS` не подставляется в командную строку, и
контейнер работал на дефолтной куче. Заменили переменную на
`JAVA_TOOL_OPTIONS` — её JVM читает сама, независимо от формы `ENTRYPOINT`.
Проверка на образе `vrptw-backend:latest`:

```text
# было: JAVA_OPTS
size_t InitialHeapSize = 65011712   {ergonomic}
size_t MaxHeapSize     = 1027604480 {ergonomic}   # ~980 МБ

# стало: JAVA_TOOL_OPTIONS
Picked up JAVA_TOOL_OPTIONS: -Xmx2g -Xms512m
size_t InitialHeapSize = 536870912  {command line} # 512 МБ
size_t MaxHeapSize     = 2147483648 {command line} # 2 ГБ
```

`jcmd` в образе нет (это JRE, а не JDK), поэтому флаги проверены через
`java -XX:+PrintFlagsFinal`. Запускать backend из compose на 8080 для проверки
не потребовалось — настройка применяется на старте JVM.

## Вывод

На реальном размере матрицы и трёх днях по 400 нарядов **все события
укладываются в 10 с** (максимум 8,15 с), `POST /plan` — в 300 с, `GET /plan` —
в 30 с. Критический сценарий из задачи не воспроизвёлся: даже без кэша
справочника и матрицы разбор JSONB добавляет к событию порядка 1,0–1,1 с поверх
5 с солвера. Кэш уменьшит этот запас ещё больше, но и без него нарушений нет.
