# API и сценарий проверки

Документ описывает контракт, который реализован, и порядок вызовов, повторяющий проверку
организаторов. Спека организаторов — `api_spec.yaml` (в корне репозитория её нужно держать
рядом с кодом).

## 1. Эндпоинты

| Метод | Путь | Что делает | Коды |
|---|---|---|---|
| GET | `/api/v1/health` | готовность, `{"status":"ok","team":"С-42","version":"0.1.0"}` | 200 |
| PUT | `/api/v1/reference` | справочники: СЦ, сотрудники, узлы доступа, типы работ | 200, 400, 422 |
| PUT | `/api/v1/reference/travel-matrix` | единая матрица времени в пути | 200, 400, 422 |
| PUT | `/api/v1/days/{date}` | наряды дня + модельное время `now` | 200, 400, 409, 422 |
| POST | `/api/v1/days/{date}/plan` | построить план (`plan_version = 1`) | 200, 404, 409 |
| GET | `/api/v1/days/{date}/plan` | текущая версия плана | 200, 404 |
| POST | `/api/v1/days/{date}/events` | событие + перепланирование | 200, 404, 409, 422 |
| GET | `/api/v1/ui/days` | загруженные дни (для интерфейса) | 200 |
| GET | `/api/v1/ui/days/{date}` | наряды дня с учётом событий | 200, 404 |
| GET | `/api/v1/ui/reference` | справочники (для интерфейса) | 200, 409 |

Пути `/api/v1/ui/**` — дополнительные, спека организаторов их не описывает и разрешает
дополнительные эндпоинты под другими путями. Они нужны, чтобы интерфейс диспетчера брал
справочники и наряды из сервиса, а не из собственных моков.

Базовый путь `/api/v1`, порт `8080`, `Content-Type: application/json`, авторизации нет.

Ошибки — всегда `ErrorResponse` с кодом и сообщением; состояние сервиса при ошибке не меняется.

## 2. Порядок вызовов (как у валидатора)

```
1. GET  /health                          ждём 200 не дольше 120 с после старта
2. PUT  /reference                       один раз за прогон, лимит 60 с
3. PUT  /reference/travel-matrix         один раз за прогон, лимит 60 с
4. PUT  /days/2026-10-26                 лимит 30 с, задаёт now
5. POST /days/2026-10-26/plan            лимит 300 с, иначе день не оценивается
6. POST /days/2026-10-26/events  × N     лимит 10 с на событие, по возрастанию timestamp
   GET  /days/2026-10-26/plan  × N       сразу после события — актуальная версия
7. GET  /days/2026-10-26/plan            итоговый план, по нему считаются метрики
```

Шаги 2–3 — один раз, 4–7 — для каждого дня. Загрузка нового дня сбрасывает состояние
предыдущего дня (план, события, версии), справочники и матрица сохраняются.

## 3. Модельное время

Сервис **не читает системные часы**. Время идёт так:

- при загрузке дня — `DayInput.now`;
- после каждого события — `timestamp` этого события;
- все расчёты (слоты, смены, перерывы) ведутся от этого времени.

Формат — ISO 8601 со смещением (`2026-10-26T09:00:00+05:00`). `JacksonConfig` отключает
`ADJUST_DATES_TO_CONTEXT_TIME_ZONE`, поэтому смещение `+05:00` сохраняется в ответах,
а не приводится к UTC.

## 4. Проверка руками

```bash
# 1. готовность
curl -s localhost:8080/api/v1/health

# 2. справочники и матрица
curl -s -X PUT localhost:8080/api/v1/reference \
     -H 'Content-Type: application/json' -d @data/reference.json
curl -s -X PUT localhost:8080/api/v1/reference/travel-matrix \
     -H 'Content-Type: application/json' -d @data/travel_matrix.json

# 3. день
curl -s -X PUT localhost:8080/api/v1/days/2026-10-26 \
     -H 'Content-Type: application/json' -d @data/day_2026-10-26.json

# 4. план
curl -s -X POST localhost:8080/api/v1/days/2026-10-26/plan | jq '.summary, .plan_version'

# 5. событие задержки
curl -s -X POST localhost:8080/api/v1/days/2026-10-26/events \
     -H 'Content-Type: application/json' -d '{
       "event_id": "EV-1", "type": "VISIT_DELAYED",
       "timestamp": "2026-10-26T16:20:00+05:00",
       "order_id": "ORD-1", "staff_id": "ST-001",
       "expected_end": "2026-10-26T16:30:00+05:00",
       "reason": "WORKS_LONGER"
     }'

# 6. план после события
curl -s localhost:8080/api/v1/days/2026-10-26/plan | jq '.plan_version, .routes[0].stops'
```

Полный автоматический прогон — `backend/smoke.sh` (20 проверок: health, справочники, матрица,
день, план, событие, версия плана, сводка).

## 5. События

| Тип | Обязательные поля | Поведение |
|---|---|---|
| `NEW_ORDER` | `order` | наряд добавляется и участвует в перепланировании |
| `ORDER_CANCELLED` | `order_id` | наряд в `cancelled`, из маршрутов убирается |
| `VISIT_DELAYED` | `order_id`, `staff_id`, `expected_end` | визит уже начат; меняется только `end`, остаток маршрута сдвигается |
| `ORDER_TRANSFERRED` | `order_id`, `staff_id`, `actual_end`, `transferred_to` | визит закончен в `actual_end`, передача в `STATION_EQUIPMENT`/`TRUNK_CABLE` |
| `STAFF_UNAVAILABLE` | `staff_id` | сотрудник исключается из решения |
| `TIME_TICK` | — | пересборка прогноза и предупреждений |

Правила:

- `event_id` идемпотентен: повтор → `200`, `duplicate = true`, `plan_version` не меняется;
- каждое принятое событие увеличивает `plan_version` на 1;
- `timestamp` не может идти назад;
- `VISIT_DELAYED`/`ORDER_TRANSFERRED` по не начатому визиту, чужому сотруднику или с `end`
  не позже планового — `422`, состояние не меняется;
- `POST /plan` после первого события — `409`.

## 6. Что ограничено сейчас

- Тело запроса по спеке — до 100 МБ (матрица около 20 МБ); отдельного лимита в коде нет,
  но на реальной матрице прогон не проверялся.
- `STAFF_UNAVAILABLE.until` игнорируется: сотрудник выбывает до конца дня.
- `RESTOCK` (заезд в СЦ за АО) не планируется.
